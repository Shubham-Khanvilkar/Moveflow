**Product**: MOVE-IN-SYNC (temporary name — do not hard-code into business logic)
**Type**: Enterprise multi-tenant employee transportation and mobility management platform
**Architecture**: Monorepo — NestJS API Gateway + Next.js Web + Python ML Service + Prisma/PostgreSQL

- Multiple companies/tenants with different organizational structures

## 3. ARCHITECTURE

### 3.1 Tech Stack

| Layer | Technology |
|---|---|
| API Gateway | NestJS (TypeScript) |
| Database | PostgreSQL 16 + Prisma ORM — **single system of record, no MongoDB** (see decision note below) |
| Cache | Redis 7 |
| Queue | BullMQ |
| Search | Elasticsearch 8 |
| WebSocket | Socket.IO |
| Web Frontend | Next.js (React) |
| ML Service | Python FastAPI + scikit-learn |
| Auth | JWT + Passport + bcrypt |
| Container | Docker + Docker Compose |
| Target Infra | Kubernetes |

**Decision: PostgreSQL only, no MongoDB.** Tenant isolation (Rule 2) needs Row-Level Security, which has no Mongo equivalent and shouldn't depend on every query remembering to filter by `companyId`. The policy-scoping resolution (Section 31), financial ledger data (rate cards, invoices, reconciliation), and geospatial queries (pickup clustering, geofencing) are all naturally relational/joined workloads — denormalizing them into documents trades one set of bugs for another. Where a Mongo-shaped need shows up, use a Postgres extension instead of a second database: **TimescaleDB** for high-frequency GPS pings, **pgvector** for AI/RAG embeddings, **JSONB** for genuinely semi-structured fields (e.g. `PolicyScope.configJson`), and the existing **Elasticsearch** for full-text search — one system of record, not two to keep in sync.

**Key architecture decision**: SUPERADMIN/MOVE-IN-ADMIN and internal staff are not tenant users, so they cannot reuse the tenant-scoped `AccessScopeGuard` (2.20) — they need a separate `PlatformAdminGuard` with no company/site/process scope, just an internal-role check against `PlatformRoleAssignment` (2.23). ## SECTION 31: MULTI-COMPANY / SITE / SHIFT POLICY SCOPING DESIGN

Addresses the gap between what's already scaffolded (Region/Site/LOB/Process/Shift models exist per Phase 2) and what's still missing to make "Transport Admin sets policies like no-show per site/process/role" actually work and actually be enforced.

### 31.1 The Model, Stated Precisely

```
Company (tenant)
  └── Project                      (1 project per company)
        └── Site                   (physical location — e.g. "Pune Hinjewadi")
              └── LOB / Process    (e.g. "Voice Support", "Back Office")
                    └── Shift      (e.g. "6AM-3PM", "Night Shift")
```

A **Transport Admin** is assigned an **AccessScope** — some subset of (company, project, site, process). Within that scope, they can *set* policies. Outside it, they can't see or touch anything — this is what `AccessScopeGuard` (task 2.20, MISSING-CRITICAL) enforces.

**Policies** (no-show grace period, call-attempt rules, ban thresholds, approval chains, cab/shuttle eligibility, cancellation windows, expense limits, etc.) can be set at **any level** of that hierarchy. A policy set at a lower level overrides one set higher up. A policy not set at any level falls back to a platform default.

This is the piece that's currently implicit rather than built: the plan has the org tree (Phase 2) and it has policy tables (`NoShowPolicyConfig`, `TransportPolicyConfig`, `ApprovalConfig`, etc.) but no single, consistent **resolution mechanism** shared across all of them.

### 31.2 Data Model

Rather than each policy type inventing its own scoping columns (which is what tends to happen organically — `NoShowPolicyConfig` gets a `siteId`, `TransportPolicyConfig` gets a different scoping shape, etc.), use **one generic scope-resolution pattern** that every policy type plugs into.

```prisma
// One row per (policy type, scope level, scope target) — no per-policy-table scoping columns
model PolicyScope {
  id          String   @id @default(uuid())
  companyId   String
  scopeLevel  ScopeLevel      // PLATFORM | COMPANY | SITE | PROCESS | SHIFT
  siteId      String?         // set when scopeLevel = SITE or narrower
  processId   String?         // set when scopeLevel = PROCESS or narrower
  shiftId     String?         // set when scopeLevel = SHIFT

  policyType  PolicyType      // NO_SHOW | CANCELLATION | BAN | APPROVAL | EXPENSE_LIMIT | ...
  configJson  Json            // the actual policy payload — shape depends on policyType

  setByUserId String          // which Transport Admin set this
  setByRole   String          // their role at time of setting — audit trail
  effectiveFrom DateTime
  effectiveTo   DateTime?     // null = still active

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@unique([companyId, scopeLevel, siteId, processId, shiftId, policyType, effectiveFrom])
  @@index([companyId, policyType])
}

enum ScopeLevel {
  PLATFORM   // SUPERADMIN/Compliance Team-set global default — lowest priority
  COMPANY
  SITE
  PROCESS
  SHIFT      // highest priority
}
```

**Why one table instead of per-policy-type scoping columns:** every new policy type (and the spec has a dozen — no-show, ban, expense, approval, cancellation, guard requirement...) automatically gets scoping, resolution, audit, and history for free. You write the resolver once.

### 31.3 Resolution Algorithm

```
resolvePolicy(companyId, policyType, { siteId, processId, shiftId }):
  candidates = PolicyScope.where(
    companyId = companyId,
    policyType = policyType,
    effectiveTo IS NULL OR effectiveTo > now(),
    (scopeLevel = SHIFT   AND shiftId = shiftId) OR
    (scopeLevel = PROCESS AND processId = processId) OR
    (scopeLevel = SITE    AND siteId = siteId) OR
    (scopeLevel = COMPANY) OR
    (scopeLevel = PLATFORM)
  )

  return candidates.sortBy(specificity: SHIFT > PROCESS > SITE > COMPANY > PLATFORM)
                    .first()
                    .configJson
```

Most-specific-wins, same pattern as CSS specificity or firewall rule ordering.

**Concrete example — no-show grace period:**
- Platform default: 10 minutes
- Company X sets: 15 minutes (company-wide)
- Company X's Pune site sets: 20 minutes (traffic is worse there)
- Company X's Pune "Night Shift" process sets: 25 minutes (safety — don't want people stranded at night)

An employee on the Pune night shift gets 25 minutes. An employee at the same site on day shift gets 20 minutes (site default). An employee at a different site gets 15 minutes (company default).

### 31.4 Enforcement — Closing the AccessScopeGuard Gap

This design is only real if a Transport Admin **cannot write** a `PolicyScope` row outside their assigned scope:

```
POST /policies/no-show
  → AccessScopeGuard checks: does requesting user's AccessScope
    cover the (siteId, processId, shiftId) in the request body?
  → If the admin's scope is "Site: Pune only" and they submit
    a PolicyScope for a Hyderabad site → 403, audited as a
    scope-violation attempt (not just a silent reject)
```

This directly closes three items in Phase 2:
- **2.20 AccessScopeGuard** — makes the whole scoping model enforceable, not just structurally present
- **2.21 maxScopeLevel** — an admin's `AccessScope` needs a cap on which scope level they're permitted to set policy at (e.g. a Site-level Transport Admin can set SITE/PROCESS/SHIFT policies but not COMPANY-level ones)
- **2.22 Scope-violation logging** — attempts get audited, not just rejected

### 31.5 Why This Is Worth Doing as a Foundational Pass, Not Per-Feature

Right now the plan has policy config scattered across `NoShowPolicyConfig`, `TransportPolicyConfig`, `ExpensePolicyConfig`, `ApprovalConfig`, `TransportBanPolicy` — five+ tables, each likely reinventing its own idea of "what level does this apply at." Retrofitting a shared scope model after five policy types each have their own shape is a much bigger job than building the one `PolicyScope` table now and having Phase 6/10/12 policies all read through it from the start. This is the same class of decision as hierarchy-as-configuration — worth getting right before more phases build on top of per-table scoping.

## SECTION 34: DOCUMENT STORAGE — GOOGLE DRIVE INTEGRATION + KYC/AML

### 34.1 Why not just point uploads straight at Drive

Google Drive can absolutely be the storage backend — but driver documents (license, KYC ID, vehicle RC/insurance) are exactly the sensitive-document case the plan's Phase 21 secrets/storage design already worries about, so a couple of guardrails matter more than for ordinary file storage:

- Use a **Shared Drive per company** (not a personal Drive folder), owned by a Move-In-Sync service account, so access is governed by the platform's own permission model rather than Google's sharing UI — a driver or Transport Admin should never get a raw "share" link.
- The **file lives in Drive; the metadata, verification status, and audit trail live in your own DB** — Drive is a blob store here, not the system of record. This also means switching providers later (S3, Azure Blob) doesn't touch your compliance workflow.
- Treat this as one implementation of the existing **storage-provider abstraction** (Phase 21 already targets pluggable storage) — Drive for companies that want it, S3-compatible for the default, same interface underneath.

### 34.2 Data Model

```prisma
model DriverDocument {
  id             String   @id @default(uuid())
  driverId       String
  companyId      String
  docType        DocType         // LICENSE_PHOTO | VEHICLE_PHOTO | RC | INSURANCE | PUC | PERMIT | FITNESS | KYC_ID | KYC_ADDRESS_PROOF

  storageProvider StorageProvider // GOOGLE_DRIVE | S3
  driveFileId     String?         // Drive file ID, if provider = GOOGLE_DRIVE
  fileUrl         String          // resolvable URL/reference regardless of provider
  fileHash        String          // integrity check, same pattern as §49 call-evidence hashing

  documentDate    DateTime        // date the DRIVER enters (e.g. license issue/renewal date) — not the upload timestamp
  uploadedAt      DateTime @default(now())

  verificationStatus VerificationStatus  // PENDING | MATCHED | MISMATCHED | EXPIRED
  verifiedByUserId   String?             // Compliance Team member
  verifiedAt         DateTime?
  mismatchReason     String?             // required if MISMATCHED

  expiryDate      DateTime?       // for license/insurance/PUC/permit/fitness
  createdAt       DateTime @default(now())
}

model KYCVerification {
  id            String   @id @default(uuid())
  driverId      String   // or vendorId, employeeId — KYC applies wherever identity verification is needed
  companyId     String
  kycType       KYCType         // IDENTITY | ADDRESS | AML_SCREENING
  status        KYCStatus       // PENDING | VERIFIED | REJECTED
  documentRef   String?         // links to DriverDocument.id if identity-doc based
  screeningResult Json?         // AML watchlist screening result, if kycType = AML_SCREENING
  verifiedByUserId String?
  verifiedAt      DateTime?
  notes           String?
}
```

### 34.2b Folder Structure, In-App Preview, and Direct Link

**Resolved**: "my drive folder" = a single Move-In-Sync-owned Drive, organized per company/driver — not each driver's personal Drive. The same abstraction also supports a company bringing its own Drive later without a redesign.

**Folder taxonomy** (auto-created on first upload, not manually maintained):
```
/MoveInSync-Documents/
  {companyId}/
    drivers/
      {driverId}/
        LICENSE_PHOTO/2026-09-04_license.jpg
        VEHICLE_PHOTO/2026-09-04_vehicle.jpg
        RC/...
        INSURANCE/...
```

**Why the raw Drive file shouldn't be linked directly to the app.** A license photo or KYC ID is exactly the kind of file where "anyone with the link can view" (Drive's normal sharing model) is the wrong default — a leaked link means a leaked ID document, and Drive's own sharing UI doesn't know about your `AccessScopeGuard`. So "visible in the app + a direct link" is built as two layers instead of one raw Drive link:

1. **In-app preview**: backend fetches file bytes from Drive via the service account (`files.get` with `alt=media`) and streams them through your own authenticated API — `GET /documents/{id}/view`. This *is* the "direct link" the app shows, it just resolves through your own auth/scope check first, so only someone authorized to see that driver's documents (Compliance Team, Transport Admin/Compliance in scope, SUPERADMIN) can actually open it — same guard as everything else in this plan, not a separate Drive-managed permission.
2. **Native Drive link (internal-only, optional)**: for Compliance Team members who already have access to the Shared Drive itself and prefer opening files natively in Drive's UI, also store the `webViewLink` — but this is only surfaced to roles that already have Shared Drive access, never to drivers/employees/managers.

Updated model:
```prisma
model DriverDocument {
  // ...fields from 34.2...
  driveFolderPath  String   // e.g. "{companyId}/drivers/{driverId}/LICENSE_PHOTO"
  driveWebViewLink String?  // native Drive link — Compliance Team (Shared Drive members) only
  thumbnailUrl     String?  // small preview for list views, generated server-side or via Drive's thumbnailLink
  // proxyViewUrl is NOT stored — it's derived: `/documents/{id}/view`, always resolved through AccessScopeGuard
}
```

**List views** (e.g. Compliance Team's review queue) use `thumbnailUrl` so scrolling a queue of 50 pending documents doesn't pull 50 full-size images. Opening a specific document calls `/documents/{id}/view` for the full-resolution proxied stream.

### 35.2 "Fill the Rest From Headcount" — Auto-Assign Reporting Chain

Rather than requiring every row to spell out Team Leader/AM/Manager by name (error-prone at scale, and what you're asking for), add an **auto-assign mode**:

- Company already has a **headcount roster** — the existing set of TLs/AMs/Managers and their current team sizes/capacity.

### 35.3 Moving and Duplicating Employees Across Team Leaders

Current model (`ManagerRelationship`, Phase 3.2) is implicitly 1:1. Replace/extend with a proper many-to-many assignment model, since you need both **moves** (with history preserved, already a stated rule in §22) and **duplicates** (an employee assigned to more than one Team Leader at once — e.g. dual reporting, temporary loaner to another team):

```prisma
model EmployeeTeamAssignment {
  id           String   @id @default(uuid())
  employeeId   String
  teamLeaderId String          // or AM/Manager — same model, different `assignmentLevel`
  assignmentLevel AssignmentLevel  // TEAM_LEADER | ASSISTANT_MANAGER | MANAGER
  isPrimary    Boolean  @default(true)   // exactly one PRIMARY per level at a time; others are secondary/duplicate
  effectiveFrom DateTime
  effectiveTo   DateTime?       // null = currently active; old rows kept, never deleted (§22 history rule)
  reason        String?         // e.g. "temporary loan to Team B", "reorg"
  changedByUserId String
}
```

- **Move**: close out the current PRIMARY row (`effectiveTo = now()`), open a new PRIMARY row under the new TL. Old row stays queryable for history.
- **Duplicate**: add a second row with `isPrimary = false` under a different TL — the employee now shows up in both TLs' team views.
- **Resolved**: a non-primary (secondary/duplicate) TL is **view-only** for that employee — cannot approve, reject, or act on their transport requests. Only the PRIMARY TL is the approver of record, unless the request is explicitly reassigned first. This avoids two TLs approving conflicting requests for the same employee.

## SECTION 37: DOCUMENT TYPE TAXONOMY — MULTI-COUNTRY, CONFIGURABLE, WITH VENDOR DOCUMENTS

### 37.1 Why This Can't Be a Hardcoded Enum

"Identity documents for all countries" is the same shape of problem as the org hierarchy (§131) and policy scoping (Section 31): a fixed enum (`AADHAAR | PAN | SSN | ...`) means every new country requires a code change. Instead, document types are **configuration data**, scoped by country, that Compliance Team/SUPERADMIN can add to without a release — the upload dropdown is just a filtered query against this table, not a hardcoded list in the frontend.

This also generalizes `DriverDocument` (Section 34) into a shared model, since vendors need documents too (registration proof, vendor ID card) and shouldn't get a separate, duplicate table.

### 37.2 Data Model

```prisma
model DocumentTypeDefinition {
  id              String   @id @default(uuid())
  countryCode     String?         // ISO 3166-1 alpha-2 (e.g. "IN", "US", "AE") — null = universal/global type
  category        DocCategory     // IDENTITY | VEHICLE | VENDOR | OTHER
  appliesTo       PartyType[]     // DRIVER | EMPLOYEE | VENDOR
  code            String          // e.g. "AADHAAR", "PAN", "RC", "PUC", "VENDOR_REG_CERT"
  label           String          // "Aadhaar Card" — shown in the dropdown
  requiresExpiry  Boolean         // drives whether the upload form asks for an expiry date
  isMandatory     Boolean         // for onboarding-completion checks
  isActive        Boolean  @default(true)
  createdByUserId String?         // SUPERADMIN/Compliance Team who added it (custom types are audited like anything else)

  @@unique([countryCode, category, code])
}

enum DocCategory { IDENTITY, VEHICLE, VENDOR, OTHER }
enum PartyType   { DRIVER, EMPLOYEE, VENDOR }

// Section 34's DriverDocument generalizes to PartyDocument (renamed, same fields otherwise):
model PartyDocument {
  id                String   @id @default(uuid())
  partyType         PartyType       // DRIVER | EMPLOYEE | VENDOR
  partyId           String          // driverId / employeeId / vendorId depending on partyType
  companyId         String
  docTypeId         String          // FK → DocumentTypeDefinition
  otherLabel        String?         // free-text label, only used when docType.code = "OTHER"

  storageProvider   StorageProvider
  driveFolderPath   String
  driveWebViewLink  String?
  thumbnailUrl      String?

  fileHash          String
  documentDate      DateTime        // date the uploader enters (issue/renewal date)
  uploadedAt        DateTime @default(now())

  verificationStatus VerificationStatus  // PENDING | MATCHED | MISMATCHED | EXPIRED
  verifiedByUserId   String?
  verifiedAt         DateTime?
  mismatchReason     String?
  expiryDate         DateTime?
}
```

### 37.3 Seed Data — Representative, Not Exhaustive

Seed a starting set; Compliance Team/SUPERADMIN extends it per country as new companies onboard from new geographies.

**Identity (India, `countryCode: "IN"`)**: Aadhaar Card, PAN Card, Voter ID, Passport, Driving Licence (also valid as ID proof)
**Identity (universal, `countryCode: null`)**: Passport (accepted everywhere as a fallback identity doc)
**Identity (extend per country as needed, e.g. `"US"`, `"AE"`, `"GB"`)**: seed only when a company from that country actually onboards — no need to pre-populate every country upfront

**Vehicle (universal)**: Registration Certificate (RC), Insurance, Fitness Certificate, Vehicle Tax / Road Tax Receipt
**Vehicle (India-specific)**: PUC (Pollution Under Control) — this is an India-only requirement; other countries have an equivalent emissions test that gets its own `code` under that country's `countryCode` rather than being forced into "PUC" universally
**Vehicle (universal)**: Permit (commercial vehicle permit, format varies by country but the category is universal)

**Vendor**: Vendor Registration Certificate, Company Incorporation Proof, GST/Tax Registration Certificate, Vendor ID Card, Vendor Insurance/Liability Certificate, Bank Account Proof (for payouts)

**Other (universal, always available)**: `code: "OTHER"` — free-text `otherLabel` field captures anything not in the list, so onboarding never blocks on a missing document type; Compliance Team can later promote a frequently-used "Other" label into a proper seeded type.

### 37.4 Upload UI Behavior

- Dropdown is filtered by: `partyType` (is this a driver, employee, or vendor upload?) + `category` (identity/vehicle/vendor) + the party's `countryCode`, falling back to universal (`countryCode: null`) types.
- Selecting "Other" reveals the free-text `otherLabel` field.
- `requiresExpiry` on the selected type drives whether the form shows a mandatory expiry-date field (identity docs like Aadhaar typically don't expire; PUC/insurance/permits do).

## SECTION 38: TRAINING & SANDBOX ENVIRONMENTS

Two different sandboxes, for two different audiences — worth keeping separate rather than one generic "sandbox," since they have different owners, different data, and different lifecycles.

### 38.1 Company Training Sandbox (for a company's own users)

**Purpose**: let a company's Transport Admins, Coordinators, Managers, TLs, and even drivers/employees *practice* the real workflows — booking, approval, dispatch, no-show, breakdown — without touching production trips, GPS, or billing.

- Each company gets a **Training Environment**, structurally a clone of their real org (same sites/processes/shifts/roles), but pointed at synthetic data — reuses the existing `Sandbox` concept from §88/17.x rather than inventing a second mechanism.
- A user's session carries a `TRAINING` vs `PRODUCTION` mode flag (same identity, explicit mode switch — not a separate login), so the same Transport Admin who manages real drivers on Monday can run new-hire training in the sandbox on Tuesday without a second account.
- **Nothing in Training mode reaches Production**: no real driver/vehicle gets dispatched, no real billing event fires, no real notification goes to a real phone number. This needs to be enforced at the service layer (every write checks the session's mode flag), not just hidden in the UI.
- Typical use: onboarding a new Transport Coordinator, or a company piloting a new site's process before going live with real employees.

### 38.2 SUPERADMIN Training/Release Sandbox (for platform updates)

**Purpose**: formalizes what's already implied by the existing rollout-group design (Phase 20, §102's Internal Test Company) into an explicit update workflow, rather than leaving "how does an update actually get validated before reaching a real company" implicit.

```
New platform update built
       ↓
Auto-enrolled into INTERNAL_TEST (the synthetic internal test company, §102)
       ↓
Automated test suite runs against it
       ↓
   FAIL ──────────────→ update blocked, feature flag stays OFF, reported back to build
       ↓ PASS
Manual/QA sign-off in the test sandbox
       ↓
   FAIL ──────────────→ blocked, same as above
       ↓ PASS
SUPERADMIN promotes to CANARY (small subset of real companies, opted in)
       ↓
Monitor error rates / rollback triggers for a defined window
       ↓
   ISSUE FOUND ────────→ ABORT (existing 20.5/§104) — affected tenants revert automatically
       ↓ CLEAN
SUPERADMIN promotes to EARLY, then GENERAL — same monitor/abort gate at each step
```

This is the same rollout-group machinery already in the plan (Phase 20, tasks 20.7–20.8, §102–104) — Section 38.2 just makes explicit that **nothing skips the INTERNAL_TEST sandbox first**, and that promotion between every stage is a SUPERADMIN action with a monitoring window, not an automatic timer.

## SECTION 39: VENDOR-LESS DRIVERS — "OTHERS" GROUP FOR BILLING

### 39.1 The Problem

Phase 11's billing/reconciliation logic (rate cards, invoice reconciliation, vendor performance) is built around `Vendor` as the billing unit. A company can have **directly-employed (in-house) drivers** who aren't linked to any third-party vendor — without a group to sit in, they either break the vendor-centric billing path or need special-case `IF vendorId IS NULL` branches scattered through Phase 11, which is exactly the kind of scattered special-casing this plan has avoided elsewhere (Section 31, 37).

### 39.2 Design — A Real Vendor Row, Not a Null Case

Rather than making `vendorId` nullable and special-casing it, **every company gets a system-seeded placeholder vendor** at company setup:

```
Vendor {
  name: "In-House / Unassigned Drivers"
  vendorType: INTERNAL          // new enum value alongside existing vendor types
  isSystemManaged: true         // cannot be deleted, cannot be renamed by the company
  companyId: <the company>
}
```

- A driver not linked to a real third-party vendor gets `vendorId = <the company's INTERNAL vendor>` by default — never left null.
- Billing, rate cards, trip cost calculation, and reconciliation (Phase 11) all run through the **exact same code path** as any other vendor — the INTERNAL vendor just has no external invoice to reconcile against (or reconciles against the company's own payroll/direct-payment record instead of a submitted vendor invoice).
- If a company later signs a real vendor contract for some of these drivers, they're simply **reassigned** to the real `Vendor` row — same `DriverVehicleAssignment`-style reassignment pattern as the employee-TL reassignment in Section 35.3, with history preserved.
- Transport Admins scoped to a site/process (per Section 31/32) see the INTERNAL vendor's drivers within their own scope only, same as any real vendor's drivers — no special visibility rule needed.

## SECTION 40: SUPERADMIN SAAS PRICING RULES ENGINE + MULTI-CURRENCY + PRODUCTION SCALE

Covers *what Move-In-Sync charges each company* (SaaS billing, Rule 17 — never mixed with transport billing, which is company-pays-vendor). Same override pattern used throughout this plan (Section 31's `PolicyScope`, Section 37's document types): pricing is **configuration**, resolved with a most-specific-wins order, not hardcoded per company.

### 40.1 Pricing Models Supported

| Model | How it works | Typical use |
|---|---|---|
| `PER_EMPLOYEE` | Flat rate × active employee headcount, billed per cycle | Predictable cost for the company, simplest for Move-In-Sync to forecast revenue on |
| `PER_KM` | Rate × total kilometers traveled across all trips in the period | Aligns Move-In-Sync's revenue with actual platform usage/value delivered |
| `PER_TRIP` | Flat rate × number of completed trips | Cab-aggregator-style — simple, but doesn't account for trip length |
| `PER_EMPLOYEE_PER_TRIP` | Flat rate (e.g. ₹5) × (employee, trip) — charged every time an employee takes a trip | Your literal example — charges scale with actual usage per person, not just headcount |
| `COMMISSION_PERCENT` | Percentage of the company's total transport spend (the vendor billing amount) | Marketplace-style — Move-In-Sync's revenue grows with the company's transport spend |
| `HYBRID` | Base subscription fee + one of the above as metered overage beyond an included allowance | Most enterprise SaaS pricing actually looks like this — predictable floor, usage-based ceiling |

### 40.2 Data Model — Same Override Pattern as PolicyScope

```prisma
model BillingPricingRule {
  id            String   @id @default(uuid())
  companyId     String?         // null = platform/plan-level default
  planId        String?         // null = company-specific override
  pricingModel  PricingModel    // PER_EMPLOYEE | PER_KM | PER_TRIP | PER_EMPLOYEE_PER_TRIP | COMMISSION_PERCENT | HYBRID
  currency      String          // ISO 4217 — "INR", "USD", "AED"...
  rateValue     Decimal         // stored as fixed-point, never float
  tierConfig    Json?           // volume tiers, e.g. [{upTo: 10000, rate: 5}, {upTo: null, rate: 4}]
  includedAllowance Json?       // for HYBRID: what's covered by the base fee before metering kicks in
  billingCycle  BillingCycle    // MONTHLY | QUARTERLY | ANNUAL
  effectiveFrom DateTime
  effectiveTo   DateTime?
  setByUserId   String          // SUPERADMIN or Finance Team
  @@unique([companyId, planId, pricingModel, effectiveFrom])
}
```

**Resolution**: company-specific rule (negotiated enterprise deal) → else the company's plan's default rule → else platform default. Identical shape to Section 31's resolver, different table.

### 40.3 Multi-Currency

- Every company has a **billing currency** set at signup (their local currency — INR, USD, AED, etc.). Invoices are always generated and legally issued in that currency — never converted after the fact.
- **Store money as integers in minor units** (paise/cents), never as float — this is a production-correctness requirement, not a nice-to-have; floating-point rounding errors compound across thousands of invoices.
- Platform-level consolidated revenue reporting (for internal use, e.g. SUPERADMIN's dashboard) converts to one **base reporting currency** using a **period-end FX snapshot rate**, stored alongside the report — never a live rate, so a report generated today and re-run next month shows the same historical number.
- Tax rules (GST for India, VAT elsewhere, sales tax in parts of the US) follow the **same configurable pattern as Section 37's document types** — a `TaxRuleDefinition` scoped by `countryCode`, not a hardcoded GST-only implementation. §84 already flags GST needs legal review before production; the same applies per-country as you expand.

### 40.4 Usage Aggregation → Invoice Pipeline

```
Nightly/period-end job (per company, run in parallel — see 40.5)
       ↓
Aggregate: active employees, total trips, total km, transport spend
       ↓
Resolve BillingPricingRule for this company (most-specific-wins)
       ↓
Apply tiering/allowance if HYBRID
       ↓
Generate invoice line items, freeze the rate + usage numbers used
       ↓
Invoice becomes IMMUTABLE (same rule as trip cost history, Rule 9/10)
       ↓
Payment collection → webhook → subscription state update
```

### 40.5 Production-Scale Considerations — This Is the Part That Actually Breaks at Volume

| Concern | Why it matters at scale | Approach |
|---|---|---|
| **Idempotent billing runs** | A retried or re-triggered billing job must never double-charge a company | Idempotency key = `(companyId, billingPeriod)`; job checks for an existing invoice before creating one |
| **Invoice immutability** | Once generated, usage/rate numbers must never silently change | Same pattern as historical trip pricing — invoice snapshots its inputs, doesn't re-query live data |
| **Parallel, sharded aggregation** | Aggregating usage for thousands of companies sequentially won't finish in a nightly window | Queue one job per company (BullMQ, already in stack), fan out across workers, not one giant cross-company query |
| **Table partitioning** | GPS pings and trip records are the highest-volume tables by far | Partition by date (e.g. monthly partitions) so a billing-period aggregation query only scans relevant partitions, not the whole table |
| **Read replicas for aggregation** | Billing queries shouldn't compete with live dispatch/booking write traffic | Aggregation reads from a replica, not the primary |
| **FX rate snapshotting** | Live FX rates would make historical reports non-reproducible | Snapshot rate stored with each cross-currency report, sourced from a rate provider on a fixed schedule (e.g. daily), not per-request |
| **Dunning at scale** | Thousands of companies means payment failures are a constant background stream, not an edge case | Automated retry schedule + state machine (ACTIVE→PAST_DUE→GRACE_PERIOD→SUSPENDED, already in Phase 17) rather than manual follow-up |
| **Billing anomaly detection** | A metering bug (e.g. GPS duplicate events double-counting km) silently inflates every affected company's invoice | Reuse Phase F's billing-forensics pattern (already designed for vendor invoices) on the platform's own usage metering — flag period-over-period usage spikes above a threshold for Finance Team review before the invoice goes out |
