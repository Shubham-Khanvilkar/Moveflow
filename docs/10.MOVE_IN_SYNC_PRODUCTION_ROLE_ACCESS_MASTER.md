# MOVE IN SYNC — PRODUCTION ROLE & ACCESS MASTER SPECIFICATION

## 1. Core rule
Move In Sync must never show the same dashboard to every user. Access is determined by:
**Role + explicit ON/OFF permissions + company/site/process/team scope.**
Backend APIs must enforce the same rules; hiding a button in the UI is not security.

Internal and external roles must remain separate.

## 2. INTERNAL ROLES
- SUPER_ADMIN — cross-tenant platform control; create/edit/suspend/archive companies; create sites/processes; create company admins; global security, audit, integrations and platform reports.
- PLATFORM_SECURITY_ADMIN — security events, access control, sessions, authentication/security policies and security audit.
- PLATFORM_AUDITOR — read-only compliance, audit and reports.
- PLATFORM_FINANCE — platform/company billing, invoices, reconciliation and financial reports.
- PLATFORM_SUPPORT — support tickets and triage; no unrestricted business mutation.
- COMPANY_ADMIN / COMPANY_OWNER — only their company; company configuration, sites/processes, delegated administrators, company reports.
- TRANSPORT_ADMIN — full transport operations inside assigned company/site/process scope; employee onboarding/offboarding; bookings; dispatch; drivers; vehicles; routes; shifts; control room; reports; can create delegated admins only when permission is ON.
- TRANSPORT_SUB_ADMIN — delegated transport operations within explicitly assigned scope; cannot exceed creator's scope.
- TRANSPORT_COORDINATOR — bookings, dispatch, assignment/reassignment, trip monitoring, no-shows and calendar/shift operations when granted.
- TRANSPORT_COMPLIANCE — compliance, policies, documents, audits and exceptions.
- TRANSPORT_MANAGER / OPERATIONS_MANAGER — operational management and reports according to scope.

## 3. EXTERNAL ROLES
- DIRECTOR — assigned company/site/process overview, approvals, analytics and reports.
- SENIOR_MANAGER — assigned multi-team/process oversight and approvals.
- MANAGER — assigned team oversight, bookings, calendar and approvals.
- ASSISTANT_MANAGER — delegated team/booking approvals.
- TEAM_LEADER — only assigned team; team booking and approvals when enabled.
- TRAINER — assigned training/team visibility.
- EMPLOYEE — own transport booking, trips, calendar and profile.
- VENDOR_ADMIN — own vendor's authorized drivers, vehicles, documents, trips and invoices.
- DRIVER — driver app: active state, trips, navigation, boarding, no-show, break/sleepy/emergency and favourite areas.
- GUARD — assigned site/trip safety and verification workflows.

## 5. SCOPE
Hierarchy:
**Company Code → Site Code(s) → Process Code(s) → Team(s) → Employee(s)**

A user may have multiple sites and multiple processes. A sub-admin cannot grant access outside the scope of the authorizing admin.

## 7. BOOKING MODES
Only show modes allowed by effective permissions.
- Own: employee's own booking.
- Team: only employees in assigned team; employee IDs/batch upload must be scope-validated.
- Process: user selects only authorized process codes.
- Site: only authorized site/process scope.
- Company: only explicitly authorized company-level users.

## 8. CALENDAR & WEEKLY BOOKING
Provide day/week/month views plus driver, vehicle, employee, team, process and site views.
Each action (view/create/edit/cancel/reassign/bulk-change) is permission-controlled.
Weekly and recurring booking must persist real records and use the same scope checks.

## 9. SHIFT CREATION
Authorized Transport Admin/Sub-admin/Coordinator users can create:
shift code/name, start/end, pickup/drop type, site, process, vehicle type/capacity, driver requirement, route/area, recurrence, effective dates, days, booking cutoff, dispatch cutoff, female-safety requirement, max route duration, capacity and status.
Support arbitrary configured intervals including 01:00, 01:30, 02:00, etc.

## 10. LIVE MAP / CONTROL ROOM
This must be a real operational feature, not a mock-up.
Show:
- Available drivers
- On-trip drivers
- Break drivers
- Sleepy drivers
- Unavailable drivers
- Pending cab assignments
- Dispatch pending
- Dispatched trips
- In-progress trips
- Completed trips
- No-shows
- Emergencies

Map must show live cab markers, driver status, trip route, pickup/drop points, sites, employee clusters and favourite-area circles.
Clicking a cab shows driver, vehicle, current/next trip, route, passenger count, last GPS update, ETA and emergency status.

## 11. DRIVER STATES
OFFLINE, ACTIVE_AVAILABLE, ASSIGNED, ON_TRIP, BREAK, SLEEPY, EMERGENCY, UNAVAILABLE.

Driver must mark **Active** in Move In Sync before receiving trips.
Driver can create favourite service-area circles.
Dispatch preference:
1. favourite-area match
2. route proximity
3. shift availability
4. capacity
5. safety constraints
6. if no favourite area, any authorized area
7. if demand exceeds favourite area, eligible drivers may be sent elsewhere.

## 12. TRIP ASSIGNMENT
Transport Admin with permission can assign/unassign/reassign a complete trip and can unassign one employee or move one/multiple employees to another cab.
Every change must preserve an immutable assignment history and recalculate capacity/route.

## 13. TRIP STATE
DRAFT → ASSIGNMENT_PENDING → DRIVER_ASSIGNED → CAB_ASSIGNED → DISPATCHED → DRIVER_EN_ROUTE → ARRIVED_AT_PICKUP → BOARDING → IN_PROGRESS → ARRIVED_AT_SITE → COMPLETED.

Driver reaching the configured pickup geofence can begin boarding. Employee OTP/one-time code is recorded where required.
Drop completion is validated using configured site/drop coordinates/geofence.
No-show records timestamp, location, reason and driver. Released capacity can be immediately used for an eligible waiting passenger according to policy.

## 14. FEMALE SAFETY
Female transport constraints must be configurable and enforced by backend dispatch logic, including guard requirements, drop sequencing, restricted locations and escalation when safe assignment is impossible. Do not hard-code these only in the frontend.

## 16. COMPANY CREATION
SUPER_ADMIN must have a fully functional Companies module. No blank or "Page Under Development" page.

Create Company fields:
legal name, company code, billing model (COMPANY/SITE/PROCESS), tax/GST information where applicable, billing address, primary contact, email, phone, status, contract dates, timezone, default transport policy and safety policy.

Post-create workflow:
1. create sites
2. create process codes
3. create company admin
4. assign site/process scope
5. configure billing
6. configure transport policies
7. configure roles/users
8. activate company

## 17. API/BACKEND REQUIREMENTS
Required API groups:
authentication, sessions, users, roles, permissions, permission overrides, companies, sites, processes, employees, teams, vendors, drivers, vehicles, bookings, shifts, trips, dispatch, routes, maps/GPS, no-shows, policies, billing, reports, audit, security events and notifications.

Every mutation requires authentication, authorization, tenant check, scope check, validation, audit event, transaction safety and idempotency where appropriate.

Do not use static dashboard numbers or demo-only buttons.

## 18. DATA INTEGRITY
Database constraints must enforce unique company codes, valid site/process relationships, employee ID uniqueness within company, valid role/permission references and no cross-tenant foreign-key relationships.
Never trust IDs supplied by the browser.

## 19. ROLE CHANGE
When a role changes, immediately:
1. save role change
2. recalculate effective permissions
3. recalculate navigation
4. recalculate dashboard
5. enforce new API permissions
6. revoke invalid old access
7. preserve explicit grants only when allowed by security policy
8. refresh/re-authenticate session if required
9. write audit event

The user must receive exactly the new role's permitted experience.

## 20. UI RULE
Do not show every module to everyone.
Example:
- `booking.own.create=OFF` → Employee cannot see Book Transport.
- `booking.team.create=ON` → Team Leader sees Book for Team and only assigned team members.
- `booking.process.create=ON` → Process booking shows only authorized process codes.

## 21. PRODUCTION ACCEPTANCE TESTS
SUPER_ADMIN can create company/site/process/company-admin and assign scope.
TRANSPORT_ADMIN can onboard/offboard employees, create delegated admin when allowed, create shifts, dispatch/reassign trips, use live map and export.
TEAM_LEADER can book only own team and cannot create companies or access unrelated processes.
EMPLOYEE can book only own transport unless explicitly granted more.
DRIVER must activate before receiving trips and cannot administer users.
Role changes must alter dashboard and API access.
Company A must never access Company B by changing URL, ID or request payload.
Excel/PDF/CSV exports must contain only authorized filtered records.

## 22. PRODUCTION BLOCKERS
Do not call the system production-ready while any of these remain:
- Page Under Development
- static/fake dashboard numbers
- demo-only buttons
- frontend-only authorization
- missing company creation
- missing role/permission assignment
- missing functional ON/OFF toggles
- missing scope enforcement
- missing audit trail
- missing tenant isolation
- missing real exports
- missing loading/error/empty states
- missing API validation
- missing database constraints
- hard-coded demo accounts as the only identity source

## 23. DEFINITION OF DONE
A module is complete only when it has a real data model, authenticated API, backend authorization, scope enforcement, working UI, persisted create/edit actions, loading/error/empty states, audit events, positive and denial tests, refresh persistence, real exports where applicable, and no production-critical placeholder.

### FINAL IMPLEMENTATION DIRECTIVE
Build this as a functioning enterprise transport-management system, not a visual mock-up.
Do not mix internal and external roles.
Do not infer access from job title alone.
Use explicit role + permission + scope.
Make every ON/OFF toggle functional.
Make every button functional.
Make backend authorization mandatory.
Make SUPER_ADMIN company creation functional.
Make Transport Admin employee onboarding/offboarding functional.
Make live map, booking, team view, weekly booking, calendar, shift creation, dispatch, no-show, optimization and report exports real persistent workflows.
